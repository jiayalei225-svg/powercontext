# 周边去哪儿：基于高德的地点推荐助手

## 1. 这个 Skill 做什么

一次任务就是一个循环：**理解需求 → 查地点 → 查步行路线 → 筛选排序 → 按统一格式回答**。

- 输入：城市、起点（坐标或地点名）、一句自然语言需求。
- 输出：最多 3 个地点。每个地点都是"从同一起点出发"的独立候选，不是一条行程。
- 每个地点给出：名称、地址、步行距离、步行时间、一句有数据依据的推荐理由。
- 不做：多站行程串联、跨城市经验迁移、长期记忆、订座下单、设备定位（起点坐标由外部提供）。

## 2. 动手查之前，先把需求拆成约束

把用户那句话翻译成下面几个字段，缺哪个用默认值补，并在回答里说明你补了什么：

1. **城市**：用户说的城市；没说就从起点地名/坐标推断。
2. **起点**：已给经纬度就直接用（`经度,纬度`，高德顺序是经度在前），不要再反查地址后重新编码，避免坐标漂移；只给了地名就先做一次地理编码拿坐标。
3. **地点类型**：咖啡馆 / 餐厅 / 公园 / 便利店 / 书店 / 药店 / 奶茶店 …… 抽出核心品类词。
4. **步行时间上限**：如"15 分钟以内""不超过 10 分钟"。这是**硬条件**。
5. **推荐数量**：用户要几个；最高不超过 3。
6. **排序偏好**：如"优先近一点""评分高的""安静的"。只有"优先近"能被路线数据直接支持，其余偏好见第 7 节。
7. **其他约束**：排除项（"不要连锁""别推荐商场里的"）、时段（"现在能坐的"）。

### 2.1 默认值

- 没指定数量 → 最多 3 个。
- 没指定步行时间上限 → 不设硬门槛，但仍按步行时间升序，近的排前面。
- 类型很笼统（"附近有什么好逛的"）→ 不要自己猜死一个品类，用"公园""商场""景点""咖啡馆"这几个宽词各搜一次，混在一起按步行时间排。
- 用户说"近一点""走得到的"但没给分钟数 → 按 15 分钟处理，并在回答里写明"按 15 分钟步行圈筛选"。

## 3. 可用工具

环境由平台统一配置，只用到高德 MCP Server 的两类能力。**以环境中实际暴露的工具名为准，按语义匹配**；常见名称如下。

**地点搜索**

- `maps_around_search`：周边搜索，主力工具。参数 `location`（中心点"经度,纬度"）、`keywords`（品类词）、`radius`（米）。返回 POI 的名称、地址、坐标、类型、距离。
- `maps_text_search`：关键词搜索，周边搜结果不够时补充。参数 `keywords`、`city`、`citylimit=true`。
- `maps_search_detail`：按 POI ID 取详情，只有需要确认营业时间时才调用。

**步行路线规划**

- `maps_direction_walking`：参数 `origin`、`destination`，都是"经度,纬度"。返回步行距离（米）和预计耗时（秒）。**这是步行距离和时间的唯一合法来源。**

**明确禁止**

- 不要用 `maps_distance` 的直线距离或球面距离当步行距离。
- 不要用"距离 ÷ 步行速度"自己算时间。
- 不要用驾车/骑行/公交路线替代步行。

## 4. 执行流程

### 第 1 步：算初筛半径

有时间上限 M 分钟时：

```
radius = min(3000, max(500, 90 × M))   // 再取整到 100 的倍数
```

例：M=15 → 1350 → 用 1400 米。

没给上限时从 1400 米起步。

半径只用来**初筛**，宁可放大。原因：直线距离恒小于步行路径距离，按步行 75–85 米/分钟估算，凡"步行 M 分钟内可达"的点，其直线距离一定不超过 90×M。所以这个半径不会漏掉合格点，也不会把超时的点当成合格——最终是否达标一律看路线查询返回的时长。

### 第 2 步：搜地点，攒候选池

1. 用核心品类词做 1 次 `maps_around_search`。
2. 候选少于 3 个时，换**同义关键词**再搜 1 次（"咖啡"↔"咖啡馆"↔"咖啡厅"，"餐厅"↔"饭馆"↔"吃饭"），必要时把 `citylimit` 的方式补一次 `maps_text_search`。
3. 每个结果都要看 `type` 字段做**类型校验**：类型串里含目标品类即算匹配（如"餐饮服务;咖啡厅;咖啡厅"匹配咖啡）；明显不符的（搜咖啡出来的是"公司""商务住宅"）直接丢弃。
4. 按 `id` 去重。**同品牌不同分店是不同地点，都要保留**。
5. 候选池最多保留 **8 个**进入路线查询：按搜索结果的距离由近到远取前 8，避免无谓调用。

### 第 3 步：逐个查步行路线

对候选池里每个 POI：`maps_direction_walking(origin=起点坐标, destination=该 POI 坐标)`，记下 `distance`（米）和 `duration`（秒）。

- 一次任务最多 8 次路线调用。
- 某条路线查询失败，重试 1 次；仍失败就把这个点排除，并在回答末尾说明"有 N 个地点因路线查询失败未纳入"。
- 距离换算：`duration / 60` 四舍五入到整数分钟；`distance` 超过 1000 米时同时给出公里数（1 位小数）。

### 第 4 步：筛、排、截断

1. **硬过滤**：`duration ≤ M × 60`，严格比较，不为"差一分钟"放行。
2. **排序**：
   - 用户说"优先近" → 按 `duration` 升序，没有例外。
   - 用户有其他偏好（评分、环境、品牌）→ 高德结果若返回了对应字段（`biz_ext.rating`、`cost` 等）可以作为次级排序键；没返回就退回按 `duration` 升序，不要编造评分。
   - 没表态 → 按 `duration` 升序。
3. **截断**：取前 min(用户要的数量, 3) 个。
4. **超时但不远的地点**：如果想提，只能单列在"超出范围"里，并明确写出"步行 X 分钟，超出 15 分钟的要求"，**绝不能混进主推荐列表**。

### 第 5 步：写回答

见第 6 节模板。

## 5. 结果不够怎么办（按顺序放宽，每步都要说明）

1. **扩半径**：1400 → 2000 → 3000 米，重新搜一次。
2. **换关键词**：同义词、上位词（"手冲咖啡馆"→"咖啡馆"→"饮品店"）。
3. **放宽品类边界**：仅当用户类型很笼统时才做（"想喝点东西"→ 咖啡馆 + 奶茶店）。
4. **仍不够** → 如实说清楚：想要 N 个，在步行 M 分钟范围内只找到 K 个符合条件的地点；已把半径扩到 X 米、换过哪些关键词；建议用户放宽时间到 M+X 分钟或换个品类。

**注意**：放宽的是"搜索范围"，不是"硬条件"。时间上限和品类是用户给的判断标准，不能为了凑数把它们改掉。

**零结果**：明确说"在步行 M 分钟范围内没有找到{类型}"，附上实际查过的范围和关键词，给 1–2 条可执行的放宽建议。不要把远处的点硬塞进来充数。

**工具报错/超时**：重试 1 次；仍失败就直说"高德的地点搜索/路线服务本次查询失败，无法给出可靠推荐"，然后停止。**任何情况下都不许用记忆里的地名、常识或估算来补一个答案。**

## 6. 回答格式

用有序列表，不要用大段散文。模板：

```
在{起点}附近，按步行{M}分钟内的要求，为你找到 {n} 家{类型}：

1. **{名称}**
   地址：{address 原文}
   步行：{distance} 米，约 {minutes} 分钟
   理由：{一句引用数据的话}

2. **{名称}**
   地址：…
   步行：…
   理由：…
```

写作规矩：

- 名称和地址**原文照抄**工具返回，不翻译、不改写、不补全门牌号、不省略"（xx店）"这类后缀。
- 距离和时间只写工具返回值，前面可以加"约"表示取整，但不能出现"大概 10 分钟"这类凭感觉的数字。
- 推荐理由必须落在数据或用户条件上，一句话说完：步行时长、距离、类型契合、用户提过的偏好。**不要写"环境优雅""很适合拍照""人不多"** —— 高德没返回这些字段。
- 数量不足时，在列表后加一段"说明："，写清缺几个、为什么缺、建议怎么放宽。
- 涉及用户问到但数据没有的信息（是否营业、要不要排队、安静程度、有没有座位、人均消费），在末尾统一加一行：`未核实：{字段}（高德未返回该信息）`。只在用户确实问到时加，不要每篇都堆。
- 全文控制在 200 字以内（不含列表条目本身），不解释你调了哪些工具、不贴 JSON、不输出坐标串。

### 6.1 范例一：常规推荐

用户：我在杭州凤起路地铁站，想找一家咖啡馆，步行不超过 15 分钟，优先近一点的。

```
在凤起路地铁站附近，按步行 15 分钟内的要求，为你找到 3 家咖啡馆：

1. **Manner Coffee（凤起路店）**
   地址：杭州市下城区凤起路 000 号 0 层
   步行：180 米，约 3 分钟
   理由：出站 3 分钟就到，是范围内步行最短的一家，适合赶时间带走一杯。

2. **星巴克（嘉里中心店）**
   地址：杭州市下城区延安路 000 号
   步行：650 米，约 9 分钟
   理由：9 分钟步行在 15 分钟限制内，座位区更大，适合坐下来待一会儿。

3. **%Arabica（湖滨银泰店）**
   地址：杭州市上城区延安路 000 号
   步行：1100 米，约 14 分钟
   理由：14 分钟已接近上限，但仍在范围内，主打单品豆。
```

（示例中的门牌号是占位符，实际输出必须逐字使用工具返回的地址。）

### 6.2 范例二：结果不足

用户：附近 5 分钟内有便利店吗？

```
在西湖文化广场附近，按步行 5 分钟内的要求，为你找到 1 家便利店：

1. **全家便利店（中山北路店）**
   地址：…
   步行：320 米，约 4 分钟
   理由：4 分钟可达，是范围内唯一符合"便利店"类型的点。

说明：步行 5 分钟内只找到 1 家。已把半径从 500 米扩到 900 米、关键词试过"便利店""超市""24 小时便利店"。若放宽到 10 分钟，周边还有 2 家可选。
```

## 7. 偏好与类型的处理细则

**关键词映射**（用户词 → 搜索词）

- 咖啡 → 咖啡馆 / 咖啡厅
- 吃饭、餐厅 → 餐厅 / 美食；想吃具体菜系就用菜系词（"火锅""面馆""日料"）
- 公园、散步、遛弯 → 公园 / 城市公园
- 买水、买东西 → 便利店 / 超市
- 奶茶 → 奶茶店 / 饮品店
- 看书 → 书店 / 图书馆
- 买药 → 药店
- 早餐 → 早餐店 / 包子铺 / 粥店

**能被数据支持的偏好**：近（步行时长）、类型、价格带（若返回 `cost`）、评分（若返回 `biz_ext.rating`，注意有的城市返回空对象）。

**不能被数据支持的偏好**：安静、人少、排队短、环境好、适合办公、有插座、宠物友好、是否营业中、是否有座位。这些一律不进推荐理由；用户明确问了，就用"未核实"标注。营业时间只在 `maps_search_detail` 明确返回了 `business_hours` 字段时才引用，且要按"高德显示营业时间 07:00–22:00"这种归因方式写。

## 8. 硬性红线

1. 地点、地址、坐标必须来自本次工具返回，一个字都不能改，也不能凭印象补一个"应该在这附近"的店。
2. 步行距离和时间只能来自步行路线查询结果，禁止直线距离、禁止按速度估算、禁止用"几分钟路程"含混带过。
3. 数量 ≤ 3，且 ≤ 用户要求的数量。
4. 步行时间上限是硬条件，超时的点不得出现在主推荐里。
5. 每个推荐都是从起点单独出发的独立方案，不要写成"先去 A 再去 B"。
6. 评分、人均、营业状态、排队、环境类描述，没有数据就不写。
7. 不在 Skill 文件、回答或日志里输出任何 API Key。
8. 不额外导出 JSON、不解释内部调用链路，除非用户明确要求。

## 9. 调用预算

控制时延，避免无意义的反复查询：

- 地点搜索：≤ 3 次（主搜 1 次 + 同义词/扩圈各 1 次）
- 步行路线：≤ 8 次
- 详情查询：≤ 3 次，且只在需要确认营业时间时用
